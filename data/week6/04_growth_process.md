# [6주차][A — 실험·데이터] 프로젝트 단계별 성장 과정

> 이슈 #68 발표 보완 자료 | **데이터 규모 증가를 성장 지표에서 제외**하고, 1~6주차 평가·검산·설명 기능의 발전과 2026-11-16 동일 조건 비교의 한계를 구분한다.

## 1. 보고서 목적과 핵심 결론

보안바다의 **LLM Defense Trade-off Lab**은 RAG 챗봇·이메일 요약기에서 프롬프트 인젝션 방어를 비교할 때, **공격 차단뿐 아니라 정상 업무 손실, 오탐, 지연, 비용, 판정 근거를 함께 확인**하도록 개발한 실험·평가 플랫폼이다.

프로젝트의 성과를 모든 보안 목표의 달성이나 상용 제품 완성으로 설명하지 않는다. **실험 사례·문서 수의 증가는 성장 근거에서 제외**하며, 초기의 공격·방어 실행에서 출발해 **평가 기준 수립 → 결과 재현·검산 → 평가 오류 발견 → 판정 근거와 미확정 상태 설명**으로 발전한 과정을 중심으로 정리한다.

2026-11-16 수행한 7개 버전 공통 조건 실험에서는 **방어 성능의 뚜렷한 향상이 관측되지 않았다.** 이를 숨기지 않고, **방어 알고리즘의 개선**과 **방어를 평가하는 플랫폼의 발전**을 구분해 설명한다.

**한 문장 소개:** “LLM 방어를 선택할 때 공격을 얼마나 막는지뿐 아니라 정상 업무를 얼마나 유지하는지, 그 판단의 근거가 무엇인지 같은 조건에서 비교하는 도구입니다.”


## 2. 단계별 성장 과정

| 단계 | 당시 수행 내용 | 새롭게 확인하거나 개선한 점 | 성과의 범위 |
|---|---|---|---|
| **1주차 — 기반 구축** | RAG·이메일 시나리오와 초기 실행·데이터 구조 정리 | 아이디어를 재현 가능한 실행 경로와 사례 구조로 구체화 | 초기 구조 구축 |
| **2주차 — 비교 기준 구체화** | 공격·정상·hard-negative 구분, D1/D2 방어와 D2 검사 위치, 평가·trace 계약 보완 | 차단 여부뿐 아니라 공격처럼 보이는 정상 요청의 손실도 구분해야 함을 확인 | 방어별 비교·추적 기반 |
| **3주차 — 정량 평가 체계** | ASR·정상 업무 성공률·FPR·지연·비용 목표 및 분모·제외 원칙 수립, dev 실험·AI 검토 | 단순 차단 여부에서 보안성과 사용성을 함께 측정하는 방식으로 발전 | `adopted_for_dev`인 탐색적 기준; holdout 미실행 |
| **4주차 — 재현과 한계 분석** | 기존 정규 dev 648출력, D2 검사 621 task의 근거 정리·검산·화면 연결 | 방어가 공격을 막아도 정상 업무를 방해할 수 있으며 수치와 원본 근거를 함께 보여야 함을 확인 | 기존 결과 재현·정합성 검증, 648건 신규 실행 아님 |
| **5주차 — 판정 자체의 검증** | h007 수동 검산, A10 재집계, hard-negative 원문 대조, 공개 사람 gold 기반 judge 검산 | 단어 포함만으로 성공 판정하는 오류와 문서 근거 부족, 자동 judge의 정확도 한계 발견 | 일부 원문 검산 완료, 도메인 독립 사람 검증 미완료 |
| **6주차 — 설명력·공통 비교 강화** | 판정 기준 근거표·대표 사례·예상 질문 정리, 별도 7개 버전 공통 조건 실험(11/16) 수행 | 결과를 동일 조건에서 재확인하고 **방어 성능 향상 미입증** 및 정상 업무 중단 위험을 수치로 확인 | 발표·보고서 정리 및 **상태 기반 실험**; 공식 ASR/FPR 미산출 |

**성장 요약:** **실행할 수 있는가 → 무엇을 측정할 것인가 → 결과를 재현할 수 있는가 → 판정이 맞는가 → 어디까지 믿을 수 있는가**로 질문의 수준이 발전했다.


## 3. 현재까지 확인한 실험·검증 범위 (데이터 규모 성장은 제외)

| 구분 | 확인된 내용 | 해석 주의 |
|---|---|---|
| 정규 dev 근거 | 최종 출력 **648건**(324+108+216), D2 검사 task **621건** | 4주차에 새로 실행한 648건이 아니며 전체 합산 ASR도 아님 |
| AI 연구 검토 | 출력 648 + D2 검사 621 = **1,269 평가 task** | 실제 사람 독립 검증과 구분 |
| 실제 모델 추가 실험 | #67 기록상 두 모델 실험 **216실행** 및 저장·이관 검증 | 다른 실험과 합산하여 한 가지 성능 지표를 만들지 않음 |
| 외부 사람 gold 기반 judge 검산 | 80쌍·160응답 중 일치 **52/160(32.5%)** | 영어 공개 기준 기반 평가기 검산이며 한국어 RAG·이메일 정확도 아님 |
| 11/16 공통 조건 재실험 | **3,024건** 원본 저장(7개 버전 × 동일 36사례 × 4모드 × 3회) | 동일 조건의 **실행 상태 비교**, 공식 ASR·정상 업무 성공률·FPR 미산출 |
| 최종 판단 | 방어 구성 추천 **보류**, 기존 holdout 미실행 | 운영 안전성 및 방어 성능 향상 입증 아님 |

### 3.1 7개 버전 동일 조건 실험에서 관측한 결과

- 원본 `full-results.zip`의 3,024개 실행 기록을 확인했다: `completed` **2,355**, `blocked` **668**, `failed` **1**(10/14 `a001/none/r2`, 시간 초과).
- D2 또는 D1+D2 조건에서 공격은 **460/504건(91.3%) 상태 차단**, 정상·hard-negative는 **208/1,008건(20.6%) 상태 차단**으로 기록됐다. **차단 비율을 ASR·FPR·정상 업무 성공률로 바꾸어 표기하지 않는다.**
- 초기 10/06과 최종 11/10의 공격 상태 차단은 모두 **66/72건**이다. **방어 성능의 성장은 입증되지 않았으며**, 정상 집단의 일부 차이는 반복 실험 변동이나 다른 실행 조건이 영향을 미쳤을 가능성을 배제할 수 없다.
- `a004`(합성 연락처 출력), `a006`(검증 토큰과 차단 비교), `h008`(정상 보안 교육 질문 차단)을 대표 검토 사례로 제시하되, 성공·실패의 **공식 판정은 gold/rubric 대조 및 사람 검산 후 확정**한다.

### 3.2 발표에서 성장으로 주장할 수 있는 것 / 없는 것

| 성장으로 설명할 수 있는 것 | 현재 주장해서는 안 되는 것 |
|---|---|
| 공격 차단과 정상 업무 손실을 **별개 지표로 설계**한 평가 기준 | ASR 5% 목표 달성 또는 방어 성공률 91.3% 확정 |
| 배치 실행·원본 trace·CSV·판정 근거를 연결한 재현·추적 기능 | 초기 대비 D2 방어 로직의 효과가 좋아졌다는 주장 |
| h007·A10·hard-negative 검산으로 자동 평가의 오류·불확실성 식별 | AI judge가 실제 한국어 서비스에서 높은 정확도를 보인다는 주장 |
| 어떤 결과가 미확정인지 공개하고 사람이 재검산할 수 있는 절차 | 실행 기록 3,024개를 모두 사람 검산 완료했다고 표현 |

## 8. 발표용 30초 요약

> “저희 프로젝트는 처음에 프롬프트 인젝션 공격을 실행하고 차단 여부를 확인하는 것에서 출발했습니다. 이후 공격 성공률, 정상 업무 유지, 판정 근거를 함께 검증하는 플랫폼으로 발전했습니다. 최근 7개 버전을 같은 조건에서 비교했지만 공격 차단 성능의 뚜렷한 향상은 확인되지 않았습니다. 대신 수동 검산과 원본 추적을 통해 자동 판정의 오류와 정상 업무 차단 문제를 밝혔고, 무엇을 아직 검증하지 못했는지까지 설명할 수 있게 됐습니다.”


## 9. 최종 결론 및 후속 과제

**완료한 것은 평가 플랫폼의 실행·비교·저장·추적 체계, 일부 원문 검산, 7개 버전 공통 조건 실행 기록 확보다. 완료하지 못한 것은 3,024건의 공식 ASR·정상 업무 성공률 산출, 모든 판정의 정확도 보증, 최종 방어 성능 인증이다.**

1~6주차의 성장은 데이터 개수나 차단 성능의 상승이 아니라 **검증 질문의 고도화**로 요약된다. 공격이 막혔는지 확인하는 단계에서, 정상 업무는 유지됐는지, 자동 판정은 맞는지, 판정 근거는 충분한지까지 검토하게 되었다. 앞으로는 독립 사람 검증과 holdout을 통해 이 평가 체계의 신뢰성을 높이는 것이 핵심 과제다.
